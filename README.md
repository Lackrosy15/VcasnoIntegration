# VcasnoIntegration

Серверная интеграция **Kommo → Вчасно.Каса Cloud API**, Java 21, Spring Boot 4.0.8, Maven.
Три режима чеков, выбор кассы в каждом запросе, сохранение ссылок и примечания в сделке.

## Эндпоинты

Административные запросы `/api/v1/**` требуют заголовок `X-API-Key` со значением `INTEGRATION_API_KEY`.
Сервис не стартует без этого ключа. API предназначен для вызова вашей серверной системой.

## Вебхук Kommo: только URL, без заголовков

Для стандартного блока Kommo «Отправить webhook» используйте URL **без подстановки ID**:

```text
https://YOUR_SERVER/webhooks/kommo/prepayment?key=WEBHOOK_SECRET
```

Сервис читает ID из POST-тела: form-urlencoded `leads[add][0][id]`, `leads[update][0][id]`,
`leads[status][0][id]` и аналогичные события; также JSON `leads: {status: [{id: ...}]}` или `lead: {id: ...}`.
Если передан ID в URL и теле, значения должны совпасть. Пакет с несколькими разными сделками отклоняется до постановки в очередь.
ID контакта, аккаунта и этапа не используются как ID сделки. Неподставленный шаблон в `leadId` — ошибка;
для штатного вебхука удалите весь параметр `&leadId=...`.

Для настройки действия в Kommo используйте один из URL (GET или POST):

```text
https://YOUR_SERVER/webhooks/kommo/full?key=WEBHOOK_SECRET&leadId=LEAD_ID
https://YOUR_SERVER/webhooks/kommo/prepayment?key=WEBHOOK_SECRET&leadId=LEAD_ID
https://YOUR_SERVER/webhooks/kommo/postpayment?key=WEBHOOK_SECRET&leadId=LEAD_ID
```

`LEAD_ID` заменяется переменной ID сделки из интерфейса Kommo; `WEBHOOK_SECRET` — значение
**KOMMO_WEBHOOK_TOKEN** из серверного `.env`. Это отдельный секрет доступа к вебхуку.
Токены Kommo и Вчасно.Каса в URL не передаются. Полный URL секретный; на reverse proxy исключите query string из access-логов.
Пустой секрет или секрет короче 32 символов отключает доступ к вебхукам. Ключ API `/api/v1/**` остаётся отдельным.

ФОП не передаётся в вебхуке. При пустом `WEBHOOK_FOP_ID` сервер выбирает кассу по полю **2110073**
и настроенным соответствиям. Для тестирования задайте на сервере **WEBHOOK_FOP_ID=test**.
Это значение фиксируется в записи очереди при приёме запроса; URL не может переопределить его.
При переходе на рабочие кассы очистите `WEBHOOK_FOP_ID`, настройте соответствия и перезапустите приложение.
Уже принятые запросы сохраняют исходный выбор кассы; не используйте тестовые сделки повторно для рабочих чеков.

Kommo получает **200** сразу после сохранения задания в БД. Это подтверждение приёма, а не выпуска чека.
Обработка идёт в фоне: создаётся чек, ссылка и примечание в сделке. Дубликат вебхука возвращает то же задание.
Временные ошибки повторяются с увеличивающейся задержкой до 60 секунд, максимум 10 попыток.
Незавершённые задания восстанавливаются после перезапуска из той же базы.
Ошибки данных, настроек кассы и исчерпание попыток переводят задание в `ACTION_REQUIRED`.
Повторная доставка вебхука не сбрасывает лимит попыток и не запускает ошибочное задание заново.

Ответ содержит `id` задания. Для диагностики администратором доступны (с `X-API-Key`):

- `GET /api/v1/webhook-jobs/{id}` — состояние, число попыток, `operationId`, ошибка.
- `POST /api/v1/webhook-jobs/{id}/retry` — повторить задание `ACTION_REQUIRED` после исправления причины.

Нужен публичный HTTPS-адрес развернутого сервиса. `localhost` из облака Kommo недоступен.
Фоновая очередь отвечает на вебхуки без ожидания кассы, с учётом [короткого таймаута Kommo](https://developers.kommo.com/docs/webhooks-general).

## Прямые административные вызовы

| Метод и путь | Результат |
|---|---|
| `POST /api/v1/leads/{leadId}/receipts/full` | Чек на весь бюджет сделки, ссылка в поле **2112656** |
| `POST /api/v1/leads/{leadId}/receipts/prepayment` | Чек на **150 грн**, ссылка в поле **2112654** |
| `POST /api/v1/leads/{leadId}/receipts/postpayment` | Чек на **бюджет − 150 грн**, ссылка в поле **2112656** |
| `GET /api/v1/operations/{operationId}` | Сохранённый статус без побочных действий |
| `POST /api/v1/operations/{operationId}/retry` | Продолжить ту же операцию после устранения ошибки |
| `GET /health` | Доступность приложения; не проверяет внешние API |

По умолчанию ФОП выбирается из поля **2110073** сделки. Отправьте запрос без тела или с `{}`.
Соответствия значений поля и касс задаются в `config/fop-routing.yml`: скопируйте
[пример](config/fop-routing.example.yml) и заполните реальные значения. Можно сопоставлять стабильный `enum-id`
опции списка или точный текст `value`. Если в записи указан `enum-id`, сопоставление идёт по нему, а не по названию.
Пока соответствия не заполнены, автоматический выбор возвращает `422` до выпуска чека.
Пустое поле, несколько значений и неоднозначное соответствие тоже блокируют выпуск.

Для явного выбора кассы (например, при тестировании) передайте:

```json
{"fopId": "test"}
```

Поддерживаются `test`, `fop1`, `fop2`. Явный `fopId` имеет приоритет над полем сделки. Значение выбирает серверный токен из настроек; сам токен в запрос передавать не нужно.
Моменты вызова и выбор ФОП остаются за вашей системой. Для других касс добавьте запись в `integration.cash-registers`.

Пример для curl:

```bash
curl -X POST http://localhost:8080/api/v1/leads/123456/receipts/prepayment \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"fopId":"test"}'
```

Пример успешного ответа:

```json
{
  "operationId": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
  "leadId": 123456,
  "type": "PREPAYMENT",
  "fopId": "test",
  "amount": 150.00,
  "status": "COMPLETED",
  "fiscalNumber": "TEST_example",
  "receiptUrl": "https://kasa.vchasno.ua/c/TEST_example",
  "error": null
}
```

Готовые запросы для HTTP Client IntelliJ IDEA: [docs/requests.http](docs/requests.http).

## Что именно попадает в чек

1. Сделка читается через `/api/v4/leads/{id}?with=catalog_elements`; бюджет — `price`.
2. Из связанных элементов выбираются товары каталога `KOMMO_PRODUCT_CATALOG_ID`. Название и цена читаются через `/api/v4/catalogs/{catalogId}/elements/{elementId}`. Количество берётся из связи с конкретной сделкой (`quantity`, также поддерживается `metadata.quantity`).
3. По умолчанию цена берётся из поля товара с `field_code=PRICE`. Для своей схемы задайте `KOMMO_PRICE_FIELD_ID` либо `KOMMO_PRICE_FIELD_CODE`. ID имеет приоритет. Товары в текстовом поле сделки не разбираются автоматически.
4. Сумма товарных строк должна точно совпасть с бюджетом. При несовпадении сервис вернёт `422` до фискализации. Сервис не придумывает цены и скидки, если в Kommo они не указаны. Если в вашей CRM используются индивидуальные цены сделки, доставка или скидки, нужно согласовать их источник и расширить адаптер `KommoClient`.
5. Полная оплата: все товары и их количества, сумма равна бюджету.
6. Предоплата: строка «Передплата» на 150 грн, товары и их полная стоимость в комментарии и `rows_pre_payment`. Используется официальный режим `task=1, subtask=1` с `cnt=0`, как требует Cloud API. Бюджет должен быть не меньше 150 грн.
7. Послеоплата: исходные товары, зачтённые 150 грн распределены по строкам пропорционально стоимости с точностью до копейки (`disc_apply_type=1`). Используется `subtask=2` и `post_payment_of_check_fn`. Итог должен быть положительным и точно совпасть с полем **2109361**; пустое или некорректное значение — ошибка.
8. Чек предоплаты должен принадлежать той же кассе. Для предоплаты, созданной этим сервисом, используется журнал. Для существующей ссылки из **2112654** дополнительно запрашивается `/api/v3/check-task/{fiscalNumber}` и проверяются касса, тип чека и сумма 150 грн. Одна предоплата не может быть зачтена в двух послеоплатах этого сервиса.
9. По умолчанию налоговая группа **2 — Без ПДВ**, средство оплаты **1 — Безготівка**, как в примерах. Для каждого рабочего ФОП они настраиваются отдельно.

Все суммы вычисляются через `BigDecimal`. Цены и суммы допускают не более двух знаков после запятой, количество — не более трёх.
После успешной фискализации в сделке создаётся обычное примечание в ленте: тип чека, сумма, ФОП, фискальный номер и ссылка. Это запись в сделке, не отдельное push-уведомление сотруднику.

## Настройка и запуск

Нужны Java 21+ и Maven 3.9+, либо Docker Compose.
Заполните настройки из [.env.example](.env.example):

| Переменная | Значение |
|---|---|
| `INTEGRATION_API_KEY` | Длинный случайный секрет для вызова эндпоинтов |
| `KOMMO_WEBHOOK_TOKEN` | Отдельный секрет в URL вебхука, минимум 32 символа |
| `WEBHOOK_FOP_ID` | `test` для тестирования вебхуков; пусто — выбор ФОП по полю сделки |
| `KOMMO_BASE_URL` | `https://ваш-поддомен.kommo.com`, без `/api/v4` |
| `KOMMO_TOKEN` | Долгоживущий токен Kommo с доступом к сделкам, каталогу, полям и примечаниям |
| `KOMMO_PRODUCT_CATALOG_ID` | ID каталога товаров, обязательный для выпуска чеков |
| `KOMMO_FOP_FIELD_ID` | Поле ФОП сделки, **2110073** |
| `KOMMO_PRICE_FIELD_ID` | ID поля цены товара, если не используется стандартный код `PRICE` |
| `VCHASNO_TEST_TOKEN` | Токен тестовой кассы, без `Bearer` |
| `VCHASNO_ZELINSKA_TOKEN`, `VCHASNO_VETROV_TOKEN` | Рабочие токены, можно добавить позже |
| `VCHASNO_ZELINSKA_TAX_GROUP`, `VCHASNO_VETROV_TAX_GROUP` | Налоговая группа соответствующего ФОП, по умолчанию 2 |
| `VCHASNO_ZELINSKA_PAYMENT_TYPE`, `VCHASNO_VETROV_PAYMENT_TYPE` | Средство оплаты соответствующего ФОП, по умолчанию 1 |
| `DATA_DIR` | Каталог журнала, по умолчанию `./data` при запуске JAR |
| `DB_PASSWORD` | Пароль локальной базы H2 |
| `PORT` | Порт приложения, по умолчанию 8080 |

ID каталога можно получить в Kommo через `GET /api/v4/catalogs`, а ID полей — `GET /api/v4/catalogs/{catalogId}/custom_fields`.
Автоматическое обновление OAuth access token не реализовано: используйте долгоживущий токен или обновляйте `KOMMO_TOKEN` своей системой.
Поддомен своего аккаунта задайте в локальном `.env`; в `.env.example` используется `https://example.kommo.com`.

### Получение токена Kommo

Создайте **приватную интеграцию** в своём аккаунте (Настройки → Интеграции → Создать интеграцию).
Для долгоживущего токена поле **Redirect URL оставьте пустым**: обработчик OAuth callback не нужен.
После сохранения откройте **Keys and scopes / Ключи и доступы → Generate long-lived token / Создать долгоживущий токен**,
выберите срок действия и сохраните токен в `KOMMO_TOKEN` локального `.env`.
Это именно долгоживущий токен, а не authorization code, Secret key или Integration ID.
Если форма требует URL, проверьте, что выбрана приватная интеграция для собственного аккаунта.
Сервис не реализует OAuth callback, поэтому не указывайте выдуманную ссылку на его эндпоинт.
Основание: [приватная интеграция](https://developers.kommo.com/docs/private-integration),
[долгоживущий токен](https://developers.kommo.com/docs/long-lived-token).

Ключи касс и настройки смены задаются в кабинете Вчасно.Каса. Cloud API автоматически открывает смену при первом чеке; автозакрытие смены настройте в кабинете.

### Docker

```bash
cp .env.example .env
# Заполнить .env
docker compose up --build -d
```

Порт опубликован только на `127.0.0.1`; для вызовов с другого сервера настройте HTTPS reverse proxy.
Журнал хранится в постоянном томе `receipts`. Один экземпляр приложения, один постоянный журнал.

### Java / PowerShell

```powershell
$env:INTEGRATION_API_KEY = 'your-long-random-secret'
$env:KOMMO_BASE_URL = 'https://your-subdomain.kommo.com'
$env:KOMMO_TOKEN = 'your-kommo-token'
$env:KOMMO_PRODUCT_CATALOG_ID = '12345'
$env:VCHASNO_TEST_TOKEN = 'your-test-cash-token'
mvn verify
java -jar target/vcasno-integration-1.0.0.jar
```

При запуске из корня проекта файл `.env` читается автоматически (формат `NAME=value`, без кавычек).
Переменные окружения имеют приоритет. Файл `.env` и рабочий `config/fop-routing.yml` исключены из Git;
токены не помещаются в примеры или образ Docker. В Compose файл соответствий монтируется из `config` только для чтения.

## Повторы и ошибки

| HTTP / status | Значение и действие вызывающей системы |
|---|---|
| `200 / COMPLETED` | Чек создан, поле и примечание записаны |
| `202 / FISCAL_PENDING` | Исход фискализации ещё не подтверждён; повторить **ту же** операцию с задержкой |
| `202 / SYNC_PENDING` | Чек уже создан, но запись в Kommo не завершена; повторить ту же операцию |
| `409 / ACTION_REQUIRED` | Нужна проверка настроек/ошибки кассы; после исправления повторить ту же операцию |
| `409` с `code=RECEIPT_CONFLICT` | Уже есть другой чек или несовместимый сценарий; автоматический повтор не поможет |
| `422` с `code=INVALID_LEAD_DATA` | Исправить данные сделки и повторить создание |
| `401` | Неверный ключ API этого сервиса |
| `502` до создания операции | Ошибка чтения Kommo/кассы; повторить исходный запрос позже |

Для прямых вызовов `/api/v1/leads/**` ответ `202` не означает завершение и не ставит операцию в фоновую очередь.
Ваша система должна вызвать `/retry` или повторить исходный эндпоинт. `GET /operations/{id}` только читает статус.
Для временных ошибок используйте увеличивающуюся задержку, например 5, 15, 30, 60 секунд, без параллельных повторов.
Для `/webhooks/kommo/**` повторы выполняет фоновый обработчик очереди, как описано выше.

До отправки в кассу сервис фиксирует payload, `tag`, кассу и сумму в файловой базе. Повторная отправка использует **тот же payload и tag**, даже если сделка после этого изменилась. Это необходимо при потере ответа: изменение суммы или кассы может создать лишний чек. После подтверждения фискализации повторяется только синхронизация Kommo.

Одна сделка допускает один чек каждого типа; полная оплата исключает сценарий предоплаты/послеоплаты. Повторный вызов с другим ФОП блокируется. Существующая ссылка в поле не перезаписывается другим чеком. Подтверждённые операции возвращаются из журнала без новых внешних запросов.
При повторном запросе без `fopId` используется уже сохранённая касса, даже если поле ФОП сделки или соответствия изменились.
Это позволяет получить результат исходной операции без риска повторной фискализации на другой кассе.

Параллельные запросы по одной сделке сериализуются внутри процесса. Файловая H2 блокирует второй процесс с тем же файлом базы. Горизонтальное масштабирование не предусмотрено; для нескольких экземпляров потребуется общая БД и распределённая блокировка. Не запускайте два независимых журнала для одного рабочего аккаунта и касс.

Примечания содержат маркер операции: перед повторной записью сервис проверяет ленту, включая страницы. Это снижает риск дублирования при потере ответа; абсолютную гарантию exactly-once для примечаний Kommo без серверного idempotency key дать нельзя.

Не удаляйте журнал и не меняйте кассу, чтобы обойти `ACTION_REQUIRED`. По коду `res` проверьте причину в кабинете/документации Вчасно. Для исправления уже сохранённого некорректного payload сначала вручную установите, был ли создан чек; автоматического удаления или редактирования таких операций нет.

Для тестовой и рабочей эксплуатации используйте отдельные тестовые сделки. После тестового чека на сделке остаются ссылки и записи журнала; рабочий чек на ту же сделку намеренно блокируется.
Резервную копию каталога `data`/тома делайте при остановленном приложении. Потеря журнала ослабляет защиту от дублей при неопределённом результате внешнего запроса.

## Проверка

```bash
mvn verify
```

Автотесты используют локальные HTTP-серверы вместо реальных API: форматы запросов и авторизации, расчёты, поле наложенного платежа, ссылки и примечания, повтор после ошибки, сохранённый payload, конкурентные вызовы, смена кассы и защита эндпоинтов. Реальные чеки тесты не выпускают.
Для проверки в вашей среде нужны токены, поддомен Kommo, ID каталога и отдельная тестовая сделка. Без них доступ к аккаунтам и выпуск чека на тестовой кассе не проверены.
